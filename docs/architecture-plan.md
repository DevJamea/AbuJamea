# منصة عائلة أبو جامع — Corrected Architecture Plan

> **المراجعة النهائية قبل التنفيذ (Final Pre-Implementation)** — هذا الإصدار يتضمن كل تصحيحات الـSchema والمعمارية النهائية. التفاصيل الكاملة للقيود في `docs/database-schema.md`.

## قرار الـStack
بعد المراجعة، تم اعتماد الاستمرار على:
- Next.js (App Router)
- Drizzle ORM
- PostgreSQL

**السبب**: هذا هو المشروع الفعلي القائم حاليًا. التحويل إلى Laravel الآن سيرفع المخاطر ويؤخر التسليم دون فائدة مباشرة في مرحلة تصحيح المعمارية والـSchema.

---

## المبادئ المعمارية الأساسية
1. Database-first + Security-first.
2. لا توجد صلاحية تعتمد على الواجهة فقط.
3. عزل البيانات حسب الدور والنطاق (Role + Scope).
4. جميع العمليات الحساسة يجب أن تكون عبر Transactions مع Audit.
5. البيانات الحساسة لا تظهر ولا تُخزّن في Logs العامة.
6. كل قاعدة لا يمكن لقاعدة البيانات فرضها (cross-table أو زمنية متغيرة) لها مالك صريح في طبقة الخدمة — موثقة في "مصفوفة الإنفاذ" بـ`docs/database-schema.md`.

## نموذج الهوية (Identity Model)
تم اعتماد جدول مركزي:
- `people`

ويحمل:
- `national_id` فريد على مستوى النظام بالكامل.

وتشير إليه الجداول التالية:
- `users.person_id`
- `family_members.person_id`
- `family_profiles.head_person_id`

بهذا لا يمكن تمثيل الشخص نفسه كسجلين منفصلين داخل النظام.

### سياسة الهاتف (نهائية)
- `people.phone` (الأساسي) **nullable** على مستوى البيانات — ليس كل فرد أسرة يملك هاتفًا.
- `secondary_phone` يبقى nullable.
- عند إدخال أي منهما: **10 أرقام بالضبط** (`^[0-9]{10}$`) — مفروض بـCHECK على مستوى DB.
- **يُمنع تخزين الهاتف كـinteger** — دائمًا `varchar`.
- **هاتف Family Head الأساسي مطلوب**، ويُفرض على مستوى **Registration/Service validation** فقط (شرط "رب الأسرة" يعيش في `family_profiles` — جدول آخر — ولا يمكن لـCHECK في PostgreSQL عبور الجداول). لا تعد وتضيف `NOT NULL` على العمود.
- متطلبات Family Head نفسها لم تتغير.

## نموذج المستخدمين والحسابات — توافق النوع والدور (Canonical)

`users` يمثل حساب الدخول فقط، مفصولًا عن نموذج الشخص.

**الشكل القانوني الوحيد:**

### Family Head
```text
account_type = family_head
auth_method  = national_id
role         = family_head
person_id    != null
username     = null
```

### Family Member
```text
account_type = family_member
auth_method  = national_id
role         = family_member
person_id    != null
username     = null
```

ملاحظة: Family Member هو فرد مرتبط بشخص موجود في `people` عبر `person_id`. لا يستخدم admin username ولا بصيغة `admin-`. يمكنه تقديم طلب `independent_family` عبر حسابه المصادَق وفق القواعد النهائية المقفلة.

### Administrative
```text
account_type = administrative
auth_method  = username
username     يبدأ بـ admin-
role ∈ { branch_admin, publisher, admin, general_manager }
```

### ممنوع معماريًا
```text
حساب family_head    + أي دور غير family_head
حساب family_member  + أي دور غير family_member
حساب administrative + أي دور من { family_head, family_member }
دور guest على أي صف users (الضيف بلا حساب)
```

### حدود الإنفاذ (موثقة بقصد)
- **تفرضه قاعدة البيانات** (same-row CHECKs): `family_head → national_id + person_id`؛ `family_member → national_id + person_id`؛ `administrative → username + بادئة admin-`؛ `family_head/family_member → username IS NULL`.
- **لا تفرضه قاعدة البيانات**: توافق `account_type ↔ role` قاعدة **عبر الجداول** (`users.role_id → roles.code`)، وCHECK في PostgreSQL لا يشير لجدول آخر، ولا ننسخ `role_code` داخل `users` (ازدواج تمثيل). **يُفرض في Service/Domain transaction** عند أي إنشاء/تعديل حساب — ملزم لأي تنفيذ مستقبلي.

### RBAC
الأدوار المعتمدة: Guest / Family Head / Family Member / Branch Admin / Publisher / Admin / General Manager — مخزّنة عبر `roles`, `permissions`, `role_permissions`, `users.role_id`.

قواعد ملزمة:

- **Family Member** هو فرد أسرة مصادَق (حساب `family_member` + دور `family_member`) — يمكنه تقديم طلب تسجيل أسرة مستقلة (`registration_requests.request_type = 'independent_family'`) عبر حسابه المصادَق حصريًا، ولا يملك أي صلاحية إدارة أسرة أو محتوى.
- Publisher (أو دور النشر المخوّل وفق RBAC) هو المسؤول عن إدارة مشاركات الأرشيف المجهولة (مراجعة/معاينة/تحرير/نشر/رفض).
- **Branch Admin ليس مسؤولًا عن استعادة الحسابات عند فقدان الهاتف** إلا بسياسة مستقبلية صريحة، ولا يصفّي كلمات مرور Family Head عبر مسار فقدان الهاتف (المسار الذاتي OTP أو الدعم الفني فقط).
- لا توسيع للصلاحيات خارج المطلوب: كل صف أعلاه هو الحد الأقصى الموثق للدور.

## نموذج العائلة والأفراد — ملكية Family Head

- `family_profiles` لبيانات الأسرة، و**`family_profiles.head_person_id` هو تمثيل Family Head**.
- `family_members` لربط الأشخاص بالأسرة وصلة القرابة — **ولا يشمل الـHead**.
- الزوجات لا يوجَد لهن جدول منفصل (`family_wives` غير موجود).

### قاعدة الملكية القاطعة (منع الازدواج)
تمثيل الشخص داخل أسره يحدث **مرة واحدة بالضبط**: إما Head (`family_profiles.head_person_id`) أو Member (صف واحد في `family_members`) — **وليس الاثنين أبدًا**.

- **Family Head لا يحتاج سجلًا إضافيًا في `family_members` لمجرد كونه Head.**
- أي تنفيذ مستقبلي **يُمنع** من إنشاء تمثيل domain مكرر لنفس الشخص (صف member للـhead، أو head + member معًا ولو عبر أسرتين).
- الاستثناءية (XOR) عبر جدولين → لا يمكن CHECK في PostgreSQL → تُفرض في معاملة الخدمة: قفل صف `people` (`SELECT ... FOR UPDATE`) ثم التحقق من عدم وجود تمثيل متعارض قبل أي إدراج.

### قاعدة 4 زوجات
مدعومة تصميميًا في قاعدة البيانات عبر:
- `wife_ordinal` محصور بين 1 و4 فقط عند `relationship='wife'`.
- `UNIQUE (family_profile_id, wife_ordinal)` جزئي للزوجات.

هذا يمنع إدخال الزوجة الخامسة على مستوى DB (تحتاج رقمًا خامسًا أو رقمًا مشغولًا — كلاهما مرفوض).

**استراتيجية الـrace condition (ملزمة للتنفيذ):** التخصيص التلقائي لـ`wife_ordinal` داخل Transaction مع قفل صف `family_profiles` (`FOR UPDATE`)، مع قراءة الأرقام المشغولة واختيار رقم حر (يسمح بإعادة استخدام رقم متحرر)، والـunique index يعمل كـbackstop — أي سباق ينهار إلى 23505 فتعيد الخدمة المحاولة.

## قاعدة عمل: انتقال فرد أسرة إلى أسرة مستقلة (Member → Independent Family Head)

> قاعدة Business/Domain transaction — **ليست** CHECK عبر الجداول (غير قابل للتنفيذ في PostgreSQL). لا تتطلب تعديل schema؛ التفاصيل الداخلية في `docs/database-schema.md`.

### السيناريو

شخص مسجل حاليًا كـ **Family Member** (`account_type = family_member`، `role = family_member`) داخل أسرة أخرى، عند زواجه ورغبته في تأسيس أسرة مستقلة يمكنه تقديم **طلب** تسجيل أسرة مستقلة عبر حسابه المصادَق.

**هذا طلب (Request) وليس نقلًا فوريًا** — يمر عبر موافقة الفرع (Branch approval) ضمن دورة الطلبات المعتمدة، عبر عمود صريح **`registration_requests.request_type = 'independent_family'`** (وليس discriminator داخل الـpayload/JSON) — قرار مقفل، راجع `docs/09-architecture-review.md` (الجولة الرابعة).

### التحذير والتأكيد الإلزامي قبل التقديم

قبل إرسال الطلب تعرض الواجهة تحذيرًا واضحًا يشرح أن الشخص مسجل حاليًا ضمن أسرة أخرى، بالنص المقترح:

> "أنت مسجل حاليًا ضمن أسرة أخرى. إذا تمت الموافقة على طلب تسجيل عائلة مستقلة، سيتم إلغاء ارتباطك بأسرتك الحالية ونقلك لتصبح رب أسرة مستقلًا."

ويجب أن يؤكد المستخدم صراحةً قبل إرسال الطلب. التحذير يُعرض للشخص نفسه فقط بعد التحقق من هويته — **لا تُسرَّب تفاصيل أسرة الشخص الأصلية لأي طرف غير مخوّل**.

### عند الموافقة — معاملة واحدة ذرّية (ONE database transaction)

داخل معاملة واحدة، وبعد **إعادة التحقق من حالة الشخص الراهنة داخل المعاملة** (قفل `SELECT ... FOR UPDATE` على صف `people` — حالته قد تكون تغيرت بعد التقديم):

1. إلغاء ارتباط الشخص بأسرته الحالية (حذف صف `family_members` الخاص به).
2. إنشاء سجل `family_profiles` جديد بـ`head_person_id` = الشخص.
3. إنشاء أو تفعيل حساب Family Head للشخص حسب الحاجة (وفق مصفوفة account_type/role).
4. **الحفاظ على سجل الشخص في `people` — يُمنع حذفه مطلقًا.**
5. تسجيل العملية في `audit_logs`.
6. تسجيل معلومات العلاقة القديمة/الجديدة في الـaudit (`old_values`/`new_values`) بما يوثّق انتقال الشخص من أسرة قائمة إلى أسرة مستقلة (الأسرة السابقة + صلة القرابة → الأسرة الجديدة + Head).

أي فشل في أي خطوة → rollback كامل. التزامن يُدار داخل المعاملة بقيود الفريد القائمة (`family_members_person_uidx`, `family_profiles_head_person_uidx`) — أي تعارض ينهار إلى 23505 ويُعالج بإعادة محاولة أو رفض آمن.

### عند الرفض

يبقى الشخص member في أسرته الأصلية: لا نقل، لا إنشاء `family_profiles`، لا تفعيل حساب Family Head.

### قواعد إضافية

- من هو Family Head بالفعل **لا يمكنه** تسجيل أسرة مستقلة أخرى (قيد DB + تحقق الخدمة).
- المنتسب كـ Member **لا ينتمي لأسرتين في آن واحد** (قيد DB).
- لا يُضاف شخص كـ member لأسرة أخرى وهو منتسب بالفعل (قيد DB + Head XOR Member).
- ثابت "Head XOR Member" لا يُخترق بهذه القاعدة — الانتقال **ينقل** التمثيل (يحذف الارتباط القديم ويستحدث تمثيل Head) داخل معاملة واحدة، فلا توجد أي لحظة تمثيل مزدوج.

## Request / Approval Architecture
### Registration Request
`draft -> submitted -> pending -> approved/rejected`

### Member Request
`pending -> approved/rejected`

### Modification Request
`pending -> approved/rejected`

كل طلب يحمل: requester / branch / status / reviewer / reviewed_at / reason/note، مع CHECKs اتساق (reviewer+reviewed_at عند الحسم، وrejection_reason عند الرفض).

## عزل البيانات (Scope Enforcement) — موثق صراحة
- **Branch Admin: نطاقه فرعه فقط** — كل استعلام/كتابة يفلتر server-side بـ`branch_id` الخاص بالحساب. لا يعتمد أبدًا على فلترة الواجهة.
- **Family Head: نطاقه أسرته** — كل وصول لبيانات الأسرة/الطلبات/الإشعارات يفلتر بملكية `family_profiles.head_person_id = current person_id` (ownership-bound server-side). لا يمكن لرب أسرة قراءة/تعديل أسرة أخرى.
- **Family Member: نطاقه شخصي فقط** — يمكنه الوصول لبياناته الشخصية وتقديم طلب أسرة مستقلة عبر حسابه المصادَق، ولا يملك وصولًا لبيانات أسرته ككيان إدارة.
- **Publisher/Admin/General Manager: نطاقاتها المركزية** — النشر والإدارة العليا وإدارة الحسابات الإدارية.
- الملفات الشخصية الحساسة (هوية/هاتف/صحة) خلف Auth + Authorization + Ownership دائمًا.

## الانتهاء التلقائي للمحتوى (Automatic Expiration) — Architecture

حقيقة قاطعة: **`expire_at` لا يجعل PostgreSQL يغيّر الـstatus تلقائيًا.** لا يمر زمني يعدّل الصفوف، ولا trigger موجود. التصميم من قطعتين:

1. **الاستعلام العام (منذ اليوم الأول — لا يعتمد على أي job):**
```sql
status = 'published'
AND (expire_at IS NULL OR expire_at > NOW())
```
   (الأقواس إلزامية — `AND` أسبق من `OR`؛ مع `deleted_at IS NULL` على مستوى الخدمة.)

2. **Scheduled Job لاحق (غير منفذ الآن):** ينقل `published → expired` عند `expire_at <= now()` كتصحيح دلالي/أرشفة. حتى قبل تشغيله، المحتوى المنتهي غير ظاهر للعامة بفضل مسار الاستعلام.

الفهارس الجزئية `news_public_expiry_idx` و`announcements_public_expiry_idx` تخدم الاستعلام العام والـJob معًا.

## Audit & Sensitive Data Architecture
- `audit_logs` يسجّل (من؟ ماذا؟ متى؟ على أي سجل؟ قبل/بعد) مع IP/User-Agent — سجل append-only للعمليات الحساسة (اعتماد الطلبات، تعديل بيانات، إدارة الحسابات، أحداث OTP دون الرمز أو الهاش).
- `registration_request_attachments` تخزن `visibility='private'` افتراضيًا، مع whitelist للنوع/الحجم/العدد مفروضة بـCHECK.
- البيانات الحساسة (هوية/هاتف/صحة) ضمن نموذج وصول مقيد (Auth + Authorization + Ownership)، ولا تُكمل National IDs في الواجهات العامة ولا في الـlogs.
- الـOTP يُخزن hashed فقط (`otp_hash`) — أبدًا لا يُخزن الرمز الخام.

### أحداث Audit المطلوبة (إلزامية عند التنفيذ)

| الحدث | ما يُسجَّل |
|---|---|
| تقديم طلب أسرة مستقلة | الفاعل، الطلب، الهوية، تأكيد التحذير |
| اعتماد/رفض طلب أسرة مستقلة | الفاعل (المراجع)، الطلب، النتيجة، السبب إن وجد |
| **انتقال الأسرة المستقلة (النقل الذرّي)** | actor/target + old_values (الأسرة السابقة + صلة القرابة) + new_values (الأسرة الجديدة + Head) بما يثبت النقل من أسرة قائمة إلى أسرة مستقلة |
| استعادة كلمة المرور الذاتية (OTP) | الهوية (مقنّنة)، الحدث sent/verified/failed/locked — دون الرمز أو الهاش |
| **إعادة التعيين الإداري لكلمة المرور** | الفاعل (GM)، الحساب الهدف، الطابع الزمني، نوع العملية، النتيجة، metadata — **أبدًا لا كلمة مرور بنص صريح (حتى المؤقتة)** |
| تغييرات التسجيل الحساسة (اعتماد/رفض/تعديل بيانات أسرة/فرد) | قبل/بعد + الفاعل + الفرع |
| نشر/رفض مشاركات الأرشيف المجهولة | الفاعل (Publisher)، المشاركة، النص الأصلي/المحرَّر، النتيجة |
| عمليات الاستيراد/التصدير | الدفعة، النطاق، الفاعل، الملخص |

**يُمنع مطلقًا في الـaudit logs:** كلمات مرور بنص صريح، رموز OTP، أو بيانات شخصية حساسة غير ضرورة للغرض.

## نقاط إنفاذ الأمان (Security Enforcement Points) — للمرحلة التنفيذية

مراجعة أمنية على مستوى التوثيق — **لا يُنفَّذ شيء الآن**؛ هذه نقاط الإنفاذ الملزمة عند التنفيذ:

| التهديد | نقاط الإنفاذ المطلوبة |
|---|---|
| تعداد الحسابات (Account enumeration) | رسائل/سلوك موحّد في تدفق الاستعادة، rate limiting على خطوتي الهوية والهاتف، قصر تلميح "آخر رقمين" على ما بعد خطوة الهوية (مقايضة موثقة ومقبولة) |
| إساءة الرفع المجهول | IP throttling على مستوى الطلب (دون تحويله لتعريف مرسل دائم)، حدود حجم الطلب، قائمة MIME/extension مقيدة (CHECKs + تحقق الخدمة) |
| الملفات الخبيثة | التحقق من magic bytes لا الاكتفاء بالـcontent-type المرسل، أسماء تخزين عشوائية، تخزين حجري خاص بلا وصول عام، تنظيف metadata إن أمكن، منع التنفيذ، خدمة الملفات عبر نقاط مخوّلة فقط، (اختياري: فحص صور/AV عند التنفيذ) |
| OTP brute force | attempts ≤ max_attempts (CHECK) + قفل `locked_until` + رسائل فشل موحّدة |
| إساءة إعادة إرسال OTP | resend_count/window_started_at/last_sent_at + فترات تهدئة + قيود لكل هاتف/غرض |
| إساءة إعادة تعيين كلمة المرور | إثبات ملكية الهاتف (OTP) قبل السماح، rate limiting، audit لكل محاولة، كلمة المرور المؤقتة (إن اعتُمدت) قصيرة العمر بإلزام تغيير |
| نقل أسرة غير مصرّح | موافقة فرع إلزامية للطلب، إعادة تحقق داخل المعاملة مع `FOR UPDATE`، صلاحيات الخدمة، audit كامل قبل/بعد |
| تسريب بيانات الفروع | فلترة server-side إلزامية بـbranch_id لكل استعلام/كتابة، لا اعتماد على الواجهة، اختبارات عزل |
| وصول غير مصرّح للهويات الوطنية | دور+نطاق فقط، تقنيع في الواجهات غير الإدارية، منع الاكتمال في استجابات API، audit للقراءات الحساسة |
| وصول غير مصرّح لمعلومات صحية | نفس نموذج الهوية + أضيق نطاق (فرع/ملكية)، audit |
| إجراءات إدارية غير مصرّح بها | RBAC خلفي (لا واجهة فقط)، مصفوفة account_type/role في معاملة الخدمة، audit إلزامي لكل عملية GM |

## OTP Architecture — تصميم "التحدي الحالي" (Schema-ready)
**صف واحد بالضبط لكل `(phone, purpose)`** عبر `UNIQUE(phone, purpose)` — لا فريد جزئي.

لماذا: التحدٍ المنتهي الصلاحية يبقى `consumed_at = NULL` فيحجز فريدًا جزئيًا ويمنع إصدار OTP جديد. الـUNIQUE الكامل يستحيل ذلك.

**Resend = تحديث واحد لنفس الصف:** otp_hash جديد، expires_at جديد، تصفير attempts، تحديث last_sent_at، زيادة resend_count، تصفير consumed_at، وتصفير locked_until عند سماح سياسة الـresend. الإصدار عند غياب الصف = INSERT، وأي سباق ينهار إلى 23505 → إعادة محاولة.

يبقى OTP (هيكل أعمدة الآن؛ الإنفاذ منطق خدمة لاحقًا): **hashed / single-use / expiring / attempt-limited / rate-limited / lockable**.

لا يُحتفظ بتاريخ OTP بقصد — أحداث دورة الحياة (دون الرمز/الهاش) تذهب لـ`audit_logs`؛ لا يُضاف جدول history إلا لحاجة امتثال صريحة.

**لم يُنفذ OTP service الآن.**

## استعادة كلمة المرور (Password Recovery) — التدفق النهائي

التدفق الذاتي عبر OTP (يعيد استخدام تصميم "التحدي الحالي" كاملًا — hashed/expiry/attempts/resend limits/lockout/consumed — دون أي إضعاف):

1. **الخطوة 1:** المستخدم يُدخل رقم الهوية الوطنية (National ID).
2. **الخطوة 2:** النظام يتحقق أن الهوية تقابل حسابًا مؤهلاً (حساب Family Head نشط مرتبط بشخص).
3. **الخطوة 3:** النظام يطلب إدخال رقم الهاتف المرتبط بالحساب. يجوز عرض تلميح غير حساس فقط:
   > "رقم الهاتف المرتبط بالحساب ينتهي بـ 67"
   **يُسمح بعرض آخر رقمين فقط** — لا أكثر. على المستخدم إدخال الهاتف كاملًا.
4. **الخطوة 4:** إذا طابق الهاتف المُدخل هاتف الحساب المسجَّل: إرسال OTP → تحقق OTP → السماح بإعادة التعيين.
5. **الخطوة 5:** بعد نجاح تحقق OTP: إدخال كلمة مرور جديدة → تأكيدها → تحديثها بشكل آمن (hash).

### فقدان الوصول للهاتف المسجَّل

**لا يُحوَّل المستخدم إلى Branch Admin.** يُوجَّه إلى **عملية الدعم الفني الرسمية (Technical Support)**.

يجب التمييز المعماري بوضوح بين مسارين:

- **Self-service:** استعادة عبر OTP (ما فوق) — بإثبات ملكية الهاتف فقط.
- **Account Recovery:** عبر الدعم الفني — عملية منفصلة بإجراءات تحقق خاصة بها (خارج نطاق هذا التدفق).

> Branch Admin **ليس** مسؤولًا عن استعادة الحساب عند فقدان الهاتف (إلا بسياسة صريحة مستقبلية)، ولا يصفّي كلمات مرور Family Head عبر مسار فقدان الهاتف.

### Anti-enumeration (إلزامي عند التنفيذ)

- لا يُكشف وجود حساب لرقم هوية معين بشكل يخلق خطر تعداد الحسابات: رسائل موحّدة، سلوك متشابه، وrate limiting على خطوتي الهوية والهاتف.
- تلميح "آخر رقمين" يُعرض فقط بعد خطوة الهوية مع حد معدل — مقايضة مقبولة وموثقة (راجع Security Review).
- فشل مطابقة الهاتف لا يوضح أكثر من اللازم ما إذا كان الخلل في الهوية أم الهاتف.

## إعادة تعيين كلمة المرور إداريًا — General Manager فقط

قاعدة RBAC/عمل صريحة:

- **فقط General Manager** يمكنه إعادة تعيين/إصدار كلمة مرور حساب مستخدم آخر عبر الواجهة الإدارية.
- **لا يمكن لأي دور — ولا GM — عرض كلمة المرور بنص صريح:** العملية **إعادة تعيين/إصدار (reset/reissue)** وليست استرجاعًا (retrieval).
- السلوك الموصى به: GM يختار الحساب الهدف → يبدأ إعادة التعيين → النظام يُصدر كلمة مرور مؤقتة أو آلية إعادة تعيين وفق التصميم النهائي → **يُلزم المستخدم الهدف بتغيير كلمة المرور عند أول دخول** بعد الإعادة الإدارية.
- **تُوثَّق العملية في الـaudit إلزاميًا:** الفاعل (actor)، الحساب الهدف (target account)، الطابع الزمني، نوع العملية، النتيجة، والبيانات الوصفية ذات الصلة.
- **يُمنع منعًا باتًّا** تخزين كلمات مرور بنص صريح في الـaudit logs — حتى المؤقتة.

> **قرار مقفل (ليس Open Decision):** آلية "إلزام التغيير عند أول دخول" تُفرض عبر العمود الصريح **`users.must_change_password`** (`boolean NOT NULL DEFAULT false`). يُضبط إلى `true` عند قيام General Manager بإعادة تعيين كلمة مرور مستخدم آخر وإصدار كلمة مرور مؤقتة. عند تسجيل الدخول بكلمة المرور المؤقتة يُفرض تغيير كلمة المرور إلزاميًا قبل اعتبار الحساب في حالة طبيعية (بوابة ما بعد المصادقة)؛ بعد نجاح التغيير يُصبح `must_change_password = false`. كلمة المرور المؤقتة لا تُخزَّن كنص صريح أبدًا — يُخزَّن hash فقط وفق آلية كلمات المرور المعتمدة (`password_hash`). راجع `docs/09-architecture-review.md` (الجولة الرابعة) للقرار المقفل الكامل.

## الأرشيف (Archive)

### البنية المفاهيمية لصفحة الأرشيف

1. عنوان صفحة الأرشيف.
2. **المقدمة الثابتة للعائلة — "عائلة أبو جامع".**
3. منشورات/إصدارات الأرشيف (archive posts).

### المقدمة الثابتة (Static) — ليست محتوى قاعدة بيانات

- المقدمة التعريفية الدائمة عن "عائلة أبو جامع" هي **محتوى موقع ثابت (static site content)**:
  - **ليست** archive post.
  - **لا تُخزَّن في قاعدة البيانات** إطلاقًا.
  - **لا ترتبط** بـ`archive_posts` أو أي جدول.
- تظهر أعلى الصفحة قبل تصفّح الزوار للمنشورات، وتصف العائلة عمومًا (محتوى تاريخي/جغرافي/تعريفي **يوفّره مالك المشروع**).
- **لا يُنشأ جدول قاعدة بيانات لهذا المحتوى الثابت.** مكان الاستضافة المعتمد معماريًا: وحدة محتوى ثابت/إعدادت في التطبيق (مثل `src/content/` أو ما يعادلها) — تُحدَّد صيغة الملف النهائية عند التنفيذ، دون تنفيذ الآن.

### المشاركة العامة في الأرشيف (Anonymous Image Submission)

ميزة عامة جديدة — **بلا تسجيل دخول**:

```text
زائر → صورة + نص → مشاركة معلّقة (pending) → مراجعة Publisher
     → معاينة → تحرير النص إن لزم → نشر أو رفض
```

**يُجمع حصريًا:** الصورة + النص المرافق. **يُمنع جمع:** الاسم، الهاتف، الهوية الوطنية، البريد، بيانات الحساب، أو أي معلومات شخصية أخرى.

- **لا إشعارات للمرسل** — لا استلام ولا قبول ولا رفض.
- **لا صفحة تتبع للمرسل** — لا يعرف نتيجة مشاركته.
- **لا يُنشأ حساب** ولا يُطلب توثيق — المرسل مجهول بالكامل.
- الكيان الدائم للبيانات: جدول `archive_image_submissions` (راجع `docs/database-schema.md`) — لا أعمدة هوية مرسل فيه إطلاقًا.

**دور Publisher (أو دور النشر المخوّل وفق RBAC):**

- رؤية المشاركات المعلّقة.
- معاينة الصورة المرفوعة.
- قراءة النص المرفق.
- تحرير النص قبل النشر (يُحتفظ بالأصل `caption` ويُستخدم المحرَّر `final_caption` عند النشر).
- النشر (ينشأ `archive_posts` + `archive_images` وترتبط به المشاركة) أو الرفض.

**متطلبات الأمان (إلزامية عند التنفيذ):** أنواع MIME/extensions مسموحة فقط، حد حجم (≤ 5MB مفروض بـCHECK)، تخزين خاص/حجري قبل الاعتماد (لا وصول عام للملفات المعلّقة إطلاقًا)، تحقق من محتوى الملف (magic bytes) لا الاكتفاء بالـcontent-type المرسل، معالجة آمنة للملفات، rate limiting/anti-abuse على مستوى الطلب دون تحويله لتعريف مرسل دائم.

### قواعد إلزامية للملف

**لا يُسمح للملف بالتحكم المباشر إطلاقًا في:** معرفات قاعدة البيانات (IDs)، معرفات المستخدمين، معرفات الأدوار، الطوابع الزمنية، password hashes، أو معرفات الملكية الداخلية. هذه تُنشأ/تُدار بالنظام حصرًا.

- ورقة Reference **غير ملزمة للنظام**: قيم الـenums والفروع في قاعدة البيانات/النظام هي المرجع النهائي — تُستخدم الورقة للمطابقة والتقارير فقط.

### التحقق قبل الالتزام (Validation قبل أي كتابة نهائية)

يجب أن يشمل:

- تنسيق رقم الهوية الوطنية.
- تكرار أرقام الهوية (داخل الملف ومع السجلات القائمة).
- تنسيق الهاتف 10 أرقام بالضبط عند توفّره.
- قواعد تكرار الهاتف (قرار مقفل: مسموح — لا فريد على phone/secondary_phone، راجع `docs/09-architecture-review.md` الجولة الرابعة).
- فرع صحيح (مطابقة الاسم الرسمي).
- علاقة قرابة صحيحة (relationship ضمن الـenum).
- تاريخ ميلاد منطقي (غير مستقبلي — تحقق زمني متغير على مستوى الخدمة).
- حد 4 زوجات + `wife_ordinal` ∈ 1..4.
- قواعد ملكية Head/Member (Head XOR Member، لا انتساب مزدوج).
- تعارضات الأشخاص القائمين (national_id موجود مسبقًا).
- تعارضات الأسر القائمة.
- عزل/تفويض الفروع (المستورد لا يستورد إلا ضمن نطاق فرعه).
- بقية قيود الـdomain القائمة.

### تقرير الأخطاء قبل الالتزام (Error Report قبل final commit)

البنية المعتمدة: **مرحلتان** — (1) dry-run تحقق كامل ينتج تقرير أخطاء مفصلًا (صف/عمود/قيمة/رسالة) عبر `import_errors` وملخص الدفعة في `import_export_batches`، (2) commit نهائي لا يُنفَّذ إلا بعد مراجعة التقرير وتأكيده. لا commit جزئي صامت.

**لم يُنفَّذ المستورد الآن — مواصفة معمارية فقط.**

## ملاحظة حول CHECK Constraints
تم تجنب استخدام `CURRENT_DATE/NOW()` في CHECK الخاصة بالمنطق الزمني المتغير (مثل منع تاريخ مستقبلي) لأن هذا النوع ليس خيارًا موثوقًا معماريًا كقيد دائم — والتحقق الزمني المتغير يُفرض على مستوى Validation/Service وقت الكتابة.

كذلك تم تجنب أي محاولة CHECK cross-table (غير قابلة للتنفيذ في PostgreSQL أصلًا) — القواعد العابرة للجداول (توافق النوع/الدور، Head XOR Member) موثقة بمالك إنفاذ صريح في طبقة الخدمة.
